## Context

The v0.7 promotions proved a typed intent can drive interaction routing itself — not just read-only navigation — in one real application (`palette_afford.c`, zero raw-coordinate callbacks). Two scoped gaps were recorded at promotion time rather than hidden (limitations L15), and they share a root: **the afford graph currently compiles pointer-downs to closures for discrete acts, and nothing else.**

- A keyboard user cannot be served by intent compilation at all: focus order, activation keys, and shortcuts have no compile step. The channel axiom (A6) holds at the claim level but not at the mechanism level — one channel routes through the graph, every other channel bypasses it.
- A drag — the continuous-intent case — is begun by the app wiring `on_mouse_move`/`on_mouse_up` into a `px_interaction` by hand; the begin step does not resolve through the graph, so a region's drag-ability is not graph data.
- The legacy raw-coordinate dispatch path (`on_click` fallback) is still the default. That is an honest transition state, not an end state: if the legacy path is never retired, "type-driven routing" degrades to "an optional convenience."

**The ordering logic for v0.8 is a dependency chain, not a preference.** Keyboard affordances (Line 1) come first because the graph already holds what the query needs — the missing pieces are focus-order data and key-event compilation in `app.c`. The drag-begin seam (Line 2) needs a new afford variant that resolves a *process* rather than a closure. The dual-path retirement decision (Line 3) is deliberately last: while keyboard and drag still bypass the graph, the legacy path always has a reason to exist, and retirement would be premature. Complete the channels first; the retirement decision then has an evidence base instead of an enthusiasm base. If Lines 1–3 land, the claim "the type drives interaction routing itself" goes from **pointer-proven** to **unconditionally held** — the strongest form the 1980s CLIM claim never reached.

| Main line | What it judges | Mechanism |
|---|---|---|
| 1. Keyboard affordances | the channel axiom terminating at the pointer | focus-order data + key-event compilation over the same AFFORDS graph |
| 2. Drag-begin afford | continuous intent bypassing the graph | an afford variant that resolves a process, not a closure |
| 3. Dual-path retirement | the transition state becoming permanent | default-flip or deprecation decision on the raw-coordinate fallback |

One cross-cutting item (orca end-to-end verification — the open external condition from v0.7 Line 4) and the carried-forward conditions ledger complete the plan.

## Line 1: Keyboard affordances (highest priority)

### Problem

Regions are pointer geometry, and `px_afford_compile` resolves pointer events only. Keyboard traversal — focus order, activation keys, shortcuts compiled to the same afforded closures — does not exist. A keyboard user cannot be served by intent compilation; the strongest essence claim in the project (type-driven routing, ADR-0017) is currently single-channel.

The graph already holds what a focus query needs (which regions afford which closures); the missing pieces are focus-order data and a key-event compile step in `app.c`.

### Goal

The same afford graph serves a second input channel: focus traversal and key activation compile to the same closures pointer events compile to. Not a parallel mechanism — **the same mechanism, one more channel** (the channel axiom's mechanism judge).

### Tasks

1. Focus-order data: an explicit, app-declared order over regions (declaration order as the default; no implicit layout-derived ordering — layout is Perception's business, not Relation's).
2. `px_afford_focus_next` / `px_afford_focus_prev`-shaped queries over the AFFORDS graph — the falsifiable retire path L15a named at promotion time.
3. Key-event compilation in `app.c` (opt-in beside `intent_graph`): Tab/Shift-Tab advance focus; the activation key (Enter/Space by default) compiles the focused region's afforded closure through the same dispatch path as a pointer-down.
4. One real application exercised end-to-end by keyboard alone (see the evidence bar below) — no pointer events required to operate it.
5. Limitations L15a retirement + corpus check: do any Category D patterns that assumed pointer-only routing re-score?

### Success criteria

- A keyboard-only session drives a real application through the afford graph — zero raw-coordinate callbacks, zero pointer events.
- The focus query and the pointer compile read the same graph; no second routing ontology.
- Promotion-shaped evidence recorded; L15a retired or re-scoped with the evidence stated.

**Estimated effort**: 2–3 weeks.

## Line 2: Drag-begin afford (the process seam)

### Problem

`intent_graph` compiles pointer-downs to closures for **discrete acts**. A drag (continuous intent) is begun by the app hand-wiring `on_mouse_move`/`on_mouse_up` into a `px_interaction` — the begin step does not resolve through the afford graph, so a region's drag-ability is not graph data. `palette_afford.c` documents this boundary in place (its slider affords no closure). This is the joint obligation ADR-0017/0018 recorded at promotion time.

### Goal

An afford variant that resolves a **process** rather than a closure: a pointer-down on a draggable region compiles to a `px_interaction` (the inert-trajectory machine), not to a one-shot closure. Drag-ability becomes graph data; the app stops hand-wiring the begin step.

### Tasks

1. New evidence first (the ADR-0017/0018 obligation): a real application whose drags must be data-driven — e.g. a designer-tool palette where what drags is decided by the afford graph, not by app code.
2. The afford-process variant: `px_afford_compile` gains a resolution form whose target is an interaction process; the existing closure form is unchanged.
3. The a11y projection: AT-SPI2 exposes draggable/adjustable states — the bridge reads drag affordances from the graph.
4. L15b retirement in the same PR that lands the evidence.

### Success criteria

- A real application's drags route through the afford graph; the begin seam is gone.
- The closure form and the process form coexist without a second ontology (one graph, two resolution forms).
- L15b retired with the evidence recorded.

**Estimated effort**: 3–4 weeks (evidence application included). Dependency: Line 1 first — the ordering logic above.

---

## Line 3: Dual-path retirement decision

### Problem

`intent_graph` routing is opt-in; NULL keeps legacy raw-coordinate dispatch identical. This was the honest v0.7 transition state. If it stays forever, the essence claim degrades to "an optional convenience" — the exact drift pattern the conditions ledger exists to prevent. But retiring the fallback before Lines 1–2 land would be premature: keyboard and drag still need the legacy path today.

### Goal

A decision, not a default: once the afford path serves every channel in the real examples, either flip the default (`intent_graph` on unless opted out) or move the raw-coordinate fallback onto the [deprecation registry](../../reference/deprecation-registry.md) with a migration note — per the process ADR-0019 used for `bind_graph`.

### Tasks

1. Evidence census: which shipped examples still exercise the raw-coordinate fallback, and why (the corpus Category D score is the metric).
2. The decision ADR: default-flip vs deprecation vs explicit keep (all three outcomes are acceptable; the admission bar decides, not enthusiasm).
3. If flip/deprecate: `UPGRADING.md` migration note + changelog, in the same PR.

### Success criteria

- The decision is recorded with its evidence, whatever it is.
- If kept: the transition state is named in the canonical docs with its retirement condition — a kept transition state must at least be a *declared* one.

**Estimated effort**: 2–3 days. Ships last — deliberately after Lines 1–2.

## Cross-cutting A: orca end-to-end verification (the open external condition)

The AT-SPI2 adapter shipped behind `PX_A11Y_ATSPI` with a CI compile-probe guarding API drift; what remains is the end-to-end proof: a Planex app navigable by orca on the x11 backend. Line 1 feeds this directly — orca navigation is focus traversal, and after Line 1 focus order is graph data the bridge can project. The ledger row flips to ready only on the observed pass; until then it stays partial, honestly.

## Cross-cutting B: the ledger discipline

The conditions ledger carried forward above stays **state, not aspiration**: rows flip only in the PR that moves the capability. When v0.8 ships, each row migrates into its abstraction's canonical doc (the v0.7 practice).
